## Configure

Storybook for Web components with Vite works without extra configuration. It reads your elements from your sources or a Custom Elements Manifest you provide. The sections below cover the available setup paths and framework options.

### Component documentation

Docgen reads your elements from your sources, or from a Custom Elements Manifest you provide. You choose the generator: Storybook's built-in one reads your sources with no setup, or you provide a manifest produced by the tool you prefer, such as `@custom-elements-manifest/analyzer` or the `@wc-toolkit/cem-generator` CLI. Your JSDoc comments on elements, attributes, properties, events, slots and CSS API reach [automatic documentation](../../writing-docs/autodocs.mdx) and the [controls](../../essentials/controls.mdx) table.

Two paths provide component documentation, and which one you get depends on a single feature flag:

|                       | [`docgenServer`](../../api/main-config/main-config-features.mdx) on, the default                             | flag off                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| Reads your elements   | on the Storybook server, from your sources or from a manifest file                                           | in the browser, from a manifest you import in `.storybook/preview.ts` |
| Configure with        | nothing, or `framework.options.customElementsManifest` / `package.json#customElements` to provide a manifest | `setCustomElementsManifest()` in the preview                          |
| Powers                | controls, autodocs, code snippets, and the [components manifest](../../ai/manifests.mdx)                     | controls and autodocs                                                 |
| Updates while running | yes, your sources and the manifest file are watched                                                          | no, restart or reload after regenerating the manifest                 |

Server-side extraction is what you get unless you turn the flag off with `features: { docgenServer: false }`. The flag-off column is the path projects created before Storybook 11 use.

Attributes, properties, events, slots, CSS custom properties, CSS parts and CSS states from the manifest become argTypes. Event, slot, part and state arg keys are suffixed, such as `my-change-event`, `default-slot`, `panel-part` and `active-state`, so they never collide with attributes. CSS custom properties keep their `--name` key.

#### Choosing a manifest generator

Any tool that writes a Custom Elements Manifest (`schemaVersion` 1.x or 2.x) works. Reasons to provide your own manifest instead of using the built-in generator: you already ship one with your package, you want your library's own analyzer plugins (FAST, Stencil, Catalyst), or you want the same manifest in Storybook and in your build.

For example, with `@custom-elements-manifest/analyzer`:

<CodeSnippets path="web-components-custom-elements-manifest-generate.md" />

The analyzer writes the same manifest format for every library. Pass the plugin flag that matches how your elements declare their attributes: `--litelement` for Lit, `--fast` for FAST, `--stencil` for Stencil, `--catalyst` for Catalyst, and no flag for elements built on `HTMLElement` directly. Without the matching flag, decorator-declared attributes such as Lit's `@property()` are missing from the manifest, and Storybook cannot pair those args with attributes. Add the command to your `package.json` scripts so it runs before `storybook dev`, or run the analyzer in `--watch` mode next to Storybook.

The analyzer writes `custom-elements.json` in the current directory. If your `package.json` has a `customElements` field that points at that file, server-side docgen uses it without more configuration.

#### Server-side extraction

Nothing to set up. Storybook's built-in generator reads the elements your stories import from your TypeScript or JavaScript sources. It understands Lit and plain `HTMLElement` elements and ships with `@storybook/web-components`.

To use a manifest from another generator instead, point Storybook at the file:

<CodeSnippets path="web-components-main-config-custom-elements-manifest.md" />

Storybook looks up your elements in this order:

1. Manifests you provide:
   1. `framework.options.customElementsManifest`, relative to the Storybook config directory.
   2. The `customElements` field in the nearest `package.json`, relative to that `package.json`.
2. Sources, through the built-in generator, for tags your manifests do not declare:
   1. The file that defined the tag last time.
   2. The story file and the files reachable through its imports.
   3. The preview file and the files reachable through its imports.
   4. The tsconfig files whose sources contain the tag as a string literal.

Storybook selects the tsconfig for each story file, so monorepos and project references work. For a JavaScript project without a tsconfig, it scans only the story's folder.

Editing an element updates its controls and descriptions while Storybook runs. If the generator or TypeScript fails to load, Storybook warns once and manifest docgen keeps working.

If Storybook cannot read complete metadata, it reports the problem in the Controls table for the affected component and in the tools CLI (`npx storybook tools docs show`). These messages do not fail the build.

- Missing manifest file: `Custom Elements Manifest <path> not found yet; docs load once the analyzer writes it`
- Tag not found in manifests or sources: `No declaration for "<tag>" was found from story file <story> and preview file <preview>. Searched the tsconfig files covering those files: <tsconfigs>. Import the element module in the story or configure customElementsManifest.`
- Older web-component-analyzer manifest shape: `<path> uses the web-component-analyzer manifest shape. The Storybook docgen server reads Custom Elements Manifests only; generate one with @custom-elements-manifest/analyzer.`

The tag-not-found message includes `and preview file <preview>` only when a preview file exists. `<tsconfigs>` is `none` when no tsconfig covers the files.

If a watched manifest becomes invalid after Storybook has loaded a valid version, Storybook keeps the last valid version and reports a warning that ends with `; using the last valid version`.

For docgen to attach to a story, `meta.component` must be the tag name string, such as `component: 'demo-card'`. Metas without `component` get no docgen, and their stories show the story source in the Code panel.

#### Story snippets

With server-side docgen, Storybook generates snippets for the Code panel and the `docs-show` MCP tool from the story file. Args stories become one element with attributes from args: booleans print bare, objects print as JSON, CSS custom properties go into `style`, parts and states go into a leading `<style>` block, `*-slot` args become children, and listeners become a trailing `<script>` with `addEventListener` calls.

For stories with a `render`, Storybook reads and resolves common template shapes before re-indenting the output:

- Reads Lit `html` templates, untagged template literals and strings.
- Resolves `args.x`, destructured parameters, aliases declared in the render body, `ifDefined`, `nothing`, literal ternaries and nested templates.
- Prints `?attr` bare when truthy and drops it when falsy, prints `.prop` as its paired attribute, and adds `@event` to the listener script.

A `render` function that builds DOM in code falls back to the args form, and authored `parameters.docs.source.code` supplies the snippet directly.

Args stories generate HTML from their args:

<CodeSnippets path="web-components-story-snippet-args.md" />

```html
<style>
  lit-slots-and-css::part(panel) {
    color: rebeccapurple;
  }
</style>
<lit-slots-and-css heading="Default render" style="--slot-panel-color: teal;">
  Body <b>text</b>
  <button slot="actions">Confirm</button>
</lit-slots-and-css>
```

Template stories read the returned template:

<CodeSnippets path="web-components-story-snippet-template.md" />

```html
<lit-slots-and-css heading="Projected">
  <p>Default slot content</p>
  <button slot="actions">Confirm</button>
</lit-slots-and-css>
```

Listener args add a script after the element:

<CodeSnippets path="web-components-story-snippet-listeners.md" />

```html
<lit-events value="changed"></lit-events>
<script>
  const element = document.querySelector('lit-events');
  element.addEventListener('my-change', () => {});
</script>
```

`parameters.docs.source.code` always wins, and `parameters.docs.source.code: null` disables the snippet. See the [Source block](../../api/doc-blocks/doc-block-source.mdx) page for the full `parameters.docs.source` API.

Storybook reports a warning above the snippet instead of printing values it cannot represent. Warnings cover directives such as `classMap` or `repeat`, properties with no paired attribute, args the template never uses, imported arg values, and render functions that build DOM in code.

## Known limitations

These apply to the default server-side extraction path.

### Code snippets do not follow your controls

The snippets shown in autodocs and the Code panel are generated from your story's source, so they show the story as you wrote it. Changing a value in the controls table updates the rendered component but not the snippet next to it.

### Elements must be reachable from the story

The generator follows imports from your story file and preview file. An element registered in a module neither file imports is not found. Import the element module, or provide a manifest.

Template-function components, like the `Button`, `Header` and `Page` the starter generates, have no custom element and therefore no docgen. Their Code panel shows the story source.

### Properties without an attribute cannot be shown in HTML

Properties with no paired attribute are listed in the snippet warning. Bind them through an attribute, or write the snippet yourself with `parameters.docs.source.code`.

## FAQ

### How do I use Stencil with static Storybook builds?

If you register Stencil components with `defineCustomElements()` from the generated loader, enable Stencil's import injection so Vite can include the lazy-loaded component entry files in the static Storybook build.

For Stencil 4.26 and later:

```ts title="stencil.config.ts"
import type { Config } from '@stencil/core';

export const config: Config = {
  extras: {
    enableImportInjection: true,
  },
};
```

For older Stencil versions, use `experimentalImportInjection: true` instead.

## API

### Options

You can pass an options object for additional configuration if needed:

<CodeSnippets path="web-components-vite-framework-options.md" />

The available options are:

#### `customElementsManifest`

Type: `string | string[]`

Default: the `customElements` field of your `package.json`, else none; elements are generated from sources

Path or paths to Custom Elements Manifest files, relative to the Storybook config directory. Use it to bring a manifest from the generator of your choice; elements it does not declare are still read from your sources. This option is ignored when `docgenServer` is off.

#### `builder`

Type: `Record<string, any>`

Configure options for the [framework's builder](../../api/main-config/main-config-framework.mdx#optionsbuilder). For this framework, available options can be found in the [Vite builder docs](../../builders/vite.mdx).
